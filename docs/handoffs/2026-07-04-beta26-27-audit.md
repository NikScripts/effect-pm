# Audit — beta.26/27 (serve reform, value→ref, flat namespaces, node-status)

Full pass over the current `src` for things that are wrong, unapproved, or worth questioning. Ordered by
severity. Evidence is `file:line` against the state pulled into wow-sports (main @ `2d79d43c`, beta.27).

---

## 🔴 A. Unapproved lazy / dynamic runtime imports (policy violation)

**Rule:** lazy/dynamic imports are not to be added without sign-off. None were approved; two exist.

1. **`src/Resource.ts:2022`** — `Effect.promise(() => import("./internal/nodeStatusResource"))`
   - Added in `0b97ff01 refactor(Resource): httpServer auto-serves node-status` (beta.26/27).
   - **It's papering over a circular dependency:** `internal/nodeStatusResource.ts:23` does
     `import * as Resource from "../Resource"`, and `Resource.ts` needs `nodeStatusResource` — a `Resource ⇄
     nodeStatusResource` cycle. The file's own comment admits it: *"…without a static import cycle
     (`Resource` ⇄ this)."* The dynamic import is the workaround, not a design choice.
   - The real fix is to break the cycle (extract the shared surface `nodeStatusResource` needs out of
     `Resource` into a leaf module both import statically), not to hide it behind `import()`.
   - **Also a correctness bug — missing extension** (see §B).

2. **`src/internal/laneStoreFactory.ts:41`** — `Effect.promise(() => import("./levelLaneStoreScheduled.js"))`
   - Lazy-loads the scheduled lane-store impl only on the non-priority branch. Whether this is deliberate
     code-splitting or another cycle dodge, it's an unapproved dynamic import.

**Not flagged (verified type-only, harmless):** the other `import("…")` hits are inline *type* imports in
type position — `store/log.ts`, `store/runResource.ts` (`import("../Query").RuntimeRecordPredicate[]`),
`ApiMetrics.ts:149` (`import("effect").Stream…`). Those are standard TS, not runtime imports.

**Ask:** revert both to static imports (fixing the underlying cycle for #1); if a dynamic import is ever
genuinely required, it comes to you first.

## 🔴 B. ESM correctness — inconsistent dynamic-import extensions

- `Resource.ts:2022` imports `"./internal/nodeStatusResource"` — **no `.js`**.
- `laneStoreFactory.ts:41` imports `"./levelLaneStoreScheduled.js"` — **with `.js`**.

Under NodeNext/ESM, runtime specifiers need the extension. tsup may paper over it in the bundle, but the
source is inconsistent and the extensionless one is a latent break for anyone consuming `src` directly (which
is exactly how wow-sports vendors it). If A is reverted this evaporates; if not, add the extension.

## 🟡 C. `{ node: X }` binding is an option, not a pipe (inconsistent)

Node-binding is the **only** tag modifier passed as a constructor option:
`Resource.Tag<T>()(id, spec, { node: X })` (and the same `{ node }` on `ApiMetrics.Tag` / `Process.Tag` /
`Telemetry.Tag` / queue tags). Every sibling modifier — `distributed`, `withReadiness`, `schedule`, `result`
— is **piped**. There is no piped node-binder (`grep` for `onNode`/`atNode`/`bindNode` → none).

**Recommend** a piped `.pipe(Resource.onNode(X))` (or `Node.bind(X)`) replacing the `{ node }` option across
the tag constructors. Benefits: matches the modifier family, composes with the other `.pipe`s, unifies
binding across all five tag kinds, and drops the special third-arg option shape. (For wow-sports it rewrites
17 contract sites — worth doing once, the piped way.)

## 🟡 D. `as unknown as` — 19 sites, mostly one file

13 of 19 are in `Resource.ts` (the RPC/serve/peer machinery: `WireServiceOf`, `PeerServiceOf`, `FlatSpecOf`,
`Layer.Layer<…>`, `toLayer` params), the rest in `web/data.ts`, `QueueResource.ts`, `CustomQueueResource.ts`
(×2), `cli/index.ts`. Some are honest mapped-type boundaries TS can't reduce under a generic `S` — but 13 in
one module is a lot of erasure, and the serve reform added several. **Ask:** each should carry a one-line
justification comment, or be narrowed; otherwise they're silent holes in the type story.

## 🟢 F. `serve` / `serveRemote` as two functions (design question, not a bug)

The served-only path is `serveRemote` (consistent across `Resource`/`ApiMetrics`/`QueueResource`/
`CustomQueueResource`/`Telemetry`), `serve` is local+served. Defensible — `serveRemote` preserves the
per-resource `R` for the different-deps case. Flagging only because a piped opt-out
(`serve(…).pipe(remoteOnly)`) would parallel the §C direction; your call whether the two-function split earns
its keep.

## ✅ Verified NOT issues (checked, so they don't get re-raised)

- **`ApiMetrics.Tag` was *not* renamed to `ApiMetricsTag`.** `ApiMetrics.ts:268` → `export { tag as Tag }`;
  tests use `ApiMetrics.Tag<M>()(id)`. It's namespace-clean via `import * as ApiMetrics` (the Telemetry
  pattern). The wow-sports error was self-inflicted — we still `import { ApiMetrics }` (the dropped
  const-object). `ApiMetricsTag` is just the exported *type*, which is what TS's "did you mean" surfaced.
- **No `remoteEntry` API** — it's `serveRemote` (§F).
- **Flat-namespace "wave 2" is clean** — `QueueResource`/`Process`/`Logs`/`Query`/`ProcessStorage` export
  plain `Tag`/`serve`/`layer` (no prefixed `XTag` regressions); good via `import * as`.
